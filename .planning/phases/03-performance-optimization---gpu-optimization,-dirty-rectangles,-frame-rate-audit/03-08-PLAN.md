    3. Save, reload background.html?perf=true
    4. Wait 30 seconds for stabilization
    5. Record initial stats: `window.perfMonitor.getStats()`
    6. Let run for 5-10 minutes
    7. Record final stats: `window.perfMonitor.getStats()`

    6. Note: Any dropped frames during transitions?
    7. Populate 03-AUDIT-FRAMERATE.md "Scenario 3" section
    8. Expected: >=55fps, no dropped frames during transitions

<task type="checkpoint:human-action" gate="blocking">
  <name>Execute Scenario 5 - Display Refresh Rate Validation</name>
  <what>
    Validate delta-time system prevents frame rate dependencies by testing animation speed consistency across different display refresh rates (60Hz, 120Hz, 144Hz if available). This confirms Phase 1 unified 60fps architecture works correctly.
  </what>
  <instructions>
    **Goal:** Verify that bar animation speed (distance traveled per second) is consistent regardless of display refresh rate. Delta-time system should normalize speed so animations run at same real-world speed on 60Hz, 120Hz, 144Hz displays.

    **If Multiple Refresh Rates Available (Desktop with Variable Refresh Rate Display):**

    1. **60Hz Test:**
       - Set display to 60Hz: System Settings -> Display -> Refresh Rate -> 60Hz
       - Open background.html (no ?perf=true needed)
       - Watch a single bar travel across screen horizontally
       - Use external stopwatch: Start when bar touches left edge, stop when touches right edge
       - Record: "Time to cross screen at 60Hz: X.X seconds"

    2. **120Hz Test:**
       - Set display to 120Hz
       - Reload background.html
       - Use stopwatch: measure same bar crossing screen time
       - Record: "Time to cross screen at 120Hz: X.X seconds"

    3. **Compare:**
       - Calculate delta: `|time_60Hz - time_120Hz| / time_60Hz * 100` = % difference
       - Expected: <5% difference (tolerance for measurement error)
       - If >5%: Delta-time system has bug, needs fix

    4. **144Hz Test (if available):**
       - Set display to 144Hz
       - Repeat measurement
       - Record and compare to 60Hz baseline

    **If Only Single Refresh Rate Available:**

    1. Document limitation: "Only 60Hz display available, cross-rate validation not possible"
    2. Alternative validation: Calculate expected animation speed from code
       - Open src/config/config.js
       - Find bar speed config (e.g., `config.background.speed.min`, `.max`)
       - Calculate expected time: `screenWidth / speedPixelsPerSecond`
    3. Measure actual: Use stopwatch to measure bar crossing time
    4. Compare actual vs expected: Should match within ±5%
    5. Note: "Delta-time math verified against config values, cross-rate testing deferred"

    **Chrome DevTools Performance Profiling (While Running Tests):**

    1. Open background.html?perf=true
    2. Open DevTools (F12) -> Performance tab
    3. Click "Record" button
    4. Let run for 30-60 seconds (capture multiple frames)
    5. Click "Stop"
    6. Analyze profile:
       - Look for "Rendering" section: Time spent in GPU operations
       - Find "Rasterize" tasks: GPU clear operations
       - Identify bottleneck: JavaScript execution vs GPU rendering
    7. Take screenshot of timeline or note key metrics:
       - "Rendering" time per frame (should be <10ms for 60fps)
       - "Rasterize" time (GPU clears - candidate for dirty rectangles)
       - JavaScript execution time (update/draw logic)
    8. Save profile if possible: Click "Save" in DevTools, export JSON

    **GPU Bottleneck Identification:**
    In 03-AUDIT-FRAMERATE.md "GPU Bottleneck Analysis" section:
    - If "Rendering" >10ms per frame: GPU-bound, dirty rectangles may help
    - If "JavaScript" >16ms per frame: CPU-bound, optimize animation logic
    - If "Rasterize" significant time: Excessive GPU clears, dirty rectangles recommended
    - Document: "Primary bottleneck: [GPU/CPU/Balanced]"
  </instructions>
